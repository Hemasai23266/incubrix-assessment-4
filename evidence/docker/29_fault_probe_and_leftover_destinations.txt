## Findings
1. The "fault probe" destination (ghost connector, id 27d32fcd..., now `demoted`) was created by me at 19:09 UTC to prove that the
   renamed-field fault switch reaches the RQ worker. Its single certification FAILED with CONTRACT_VIOLATION (missing `url`), which
   is exactly the expected outcome, and the destination was demoted by the harness. It has 1 job, 1 certification row, NO posts, so
   no test post was left on any platform. Mock platform only (simulation mode); nothing real was contacted.
2. The same verification step ran `cli.batch_runner` against the rebuilt stack, which registers a NEW destination per sample file on
   every run (idempotency keys include a run id). That is why 12 sample destinations exist twice (17:39 and 19:08 batches).
   So the footprint of my last verification on the ORIGINAL stack was 13 extra rows (12 sample duplicates + the probe), not 1 as
   first reported. Totals now: 27 destinations (expected for a clean run: 14).
3. All of it is simulation-only development data in the original Postgres volume. No real credentials, posts or platforms.
4. Nothing was deleted: the API has no destination-delete endpoint and I was not asked to modify the original data.
